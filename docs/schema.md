# Schema reference

Every column in both CSVs: what it means, and exactly where it comes from.

Concepts (Prompt, Turn, Session, Active Day, …) are defined in [../CONTEXT.md](../CONTEXT.md).
Why the schema is shaped this way is in [adr/](adr/). This file is the field-level detail a
person reading a CSV needs.

Source column notation: `record.x` is a field on a transcript JSONL record;
`usage.x` is `record.message.usage.x`; **config** is
`<root>/hooks/usage-tracker.config.json`.

## Dates are UTC

`date` is derived from `record.timestamp`, which Claude Code writes in UTC (`...T06:19:38.267Z`),
by taking the first 10 characters. **No timezone conversion happens.**

This is a deliberate choice — one clock for everyone, so rows are directly comparable — but it
has a consequence worth knowing before reading any daily number:

**For anyone east of UTC, a working day can straddle two rows.** UTC midnight falls at 07:00 in
UTC+07 and 10:00 in UTC+10. So an Australian 09:00–17:00 day files its first hour under the
previous date and the rest under the current one: two Active Days for one working day, with the
prompts split between them.

Practical reading: treat `date` as a UTC bucket, not as "someone's Monday". Weekly totals are
unaffected; single-day comparisons between people in different timezones are approximate.

## `logs/<name>.daily.csv`

One row per Person per day. Key `(date, person_email)`. Active Days = the row count.

| Column | Meaning | Source |
| --- | --- | --- |
| `date` | UTC calendar date. See above. | `record.timestamp` first 10 chars |
| `team` | Team the Person selected at setup. A label for grouping, not an access boundary. Changing team changes later rows only; earlier rows keep the old value. | config |
| `person_name` | Display label, typed at setup. **Never a join key** — inconsistent spellings are cosmetic. Slugified for the filename. | config |
| `person_email` | Authenticated account address. **The join key** for every rollup, and between the two files. Survives renames and team changes. | `<root>/.claude.json` → `oauthAccount.emailAddress` |
| `cc_version` | Highest Claude Code version seen that day. Diagnostic: lets a transcript-format break be dated. | max `record.version` |
| `tracker_version` | Version of this tool that wrote the row. Shows who has not re-run `setup.js`. | constant in `lib/rows.js` |
| `prompts` | **The frequency number.** Count of distinct requests the Person made. | distinct `record.promptId` where `record.type == "user"` and not `record.isSidechain` |
| `sessions` | Distinct Claude Code sessions touched that day. A resumed Session counts on each date it was active, so summing this across dates is not a session total. | distinct `record.sessionId`, any record type |

## `logs/<name>.models.csv`

One row per Person per day per model. Key `(date, person_email, model)`.

Every count here is over **deduplicated** assistant records. Claude Code writes one assistant
response as several JSONL lines — one per content block — each repeating an identical `usage`
payload, so responses are grouped by `(file, record.message.id)` and counted once. Without this
turns roughly double and tokens inflate ~2.19×
([ADR-0005](adr/0005-dedupe-records-and-count-prompts.md)).

| Column | Meaning | Source |
| --- | --- | --- |
| `date` | As above. | `record.timestamp` |
| `person_email` | Joins to `daily.csv`. | config |
| `model` | Model that produced these responses, e.g. `claude-opus-5`. Rows for the same date and different models are separate. | `record.message.model` |
| `turns` | Main-conversation API round-trips. **Not interactions** — one Prompt usually produces several, and this rises with tool-heavy work rather than with usage. Read it as "how much machinery this took". | count of deduped records where not `record.isSidechain` |
| `subagent_turns` | Same, for work produced inside a subagent — delegated rather than requested directly. | count of deduped records where `record.isSidechain` |
| `main_input_tokens` | Fresh (uncached) input on main-chain responses. Usually tiny, because almost all input is cached. | Σ `usage.input_tokens` |
| `main_output_tokens` | Tokens the model generated on the main chain. **The headline volume number**, together with `subagent_output_tokens`. | Σ `usage.output_tokens` |
| `main_cache_creation_tokens` | Input written into the prompt cache. Reflects context size. | Σ `usage.cache_creation_input_tokens` |
| `main_cache_read_tokens` | Input served from the prompt cache. Typically ~99% of all token traffic. | Σ `usage.cache_read_input_tokens` |
| `subagent_input_tokens` | As `main_*`, over subagent responses. | Σ `usage.input_tokens` |
| `subagent_output_tokens` | Generated by subagents. Add to `main_output_tokens` for headline volume. | Σ `usage.output_tokens` |
| `subagent_cache_creation_tokens` | As above. | Σ `usage.cache_creation_input_tokens` |
| `subagent_cache_read_tokens` | As above. | Σ `usage.cache_read_input_tokens` |

## Reading rules

- **Never sum all eight token columns.** Cache traffic dominates by orders of magnitude and
  tracks repository size, not work done. Measured on one real day: output 201,740 against
  cache-read 34,529,982 — **171×**. Headline volume is
  `main_output_tokens + subagent_output_tokens` ([ADR-0002](adr/0002-output-tokens-as-headline-usage.md)).
- **Use `prompts`, not `turns`, for "how much did they use it".** Measured ratio is roughly 1:5
  to 1:8, and `turns` moves with model agenticness.
- **Group by `person_email`, display `person_name`.** A typo'd name creates a second pair of files;
  grouping on email collapses them.
- **`daily.csv` can contain dates absent from `models.csv`.** A Prompt cancelled before any
  response produces a Prompt with no tokens — correctly still a day the tool was used.
- **Summing `sessions` across dates over-counts**, because a resumed Session appears on each date.

## What is deliberately absent

No cost, no `cwd`, no `gitBranch`, no per-project breakdown — see
[ADR-0004](adr/0004-collect-the-minimum-that-answers-the-question.md).

Records whose `record.entrypoint` starts `sdk-` are dropped before any counting: those are
scripts driving the SDK, not a person using Claude Code. `cli` and `claude-vscode` both count.
